# AI와 함께 만든 바이브코딩 개발 흐름

이 문서는 `vibe-learning`을 설계하고 구현한 과정을 AI 사용법 관점에서 정리한 기록입니다. 핵심은 AI에게 한 번에 완성본을 요구하는 것이 아니라, 작은 작업 단위로 나누고 매 단계의 결과를 사람이 확인하는 것입니다.

## 1. 전체 흐름

```text
문제 정의
→ 범위와 금지사항 결정
→ 저장소와 규칙 확인
→ 설계 문서 작성
→ 한 기능 구현
→ 테스트와 코드 리뷰
→ 문제 수정
→ 커밋
→ 다음 기능 구현
→ 빌드·E2E·배포 검증
→ 운영 문서 갱신
```

AI는 구현 속도를 높였지만 다음 결정은 사람이 책임졌습니다.

- 무엇을 만들고 무엇을 만들지 않을지
- 확인되지 않은 영상 정보를 어떻게 다룰지
- 사용자 데이터를 어디에 저장할지
- 보안상 허용하지 않을 기능은 무엇인지
- 테스트 결과와 배포 결과를 실제로 확인했는지

## 2. 설계 단계에서 AI를 사용한 방법

### 2.1 아이디어를 기능 목록으로 바꾸기

처음부터 “사이트를 만들어라”라고 요청하지 않고, 사용자 가치를 화면과 데이터 단위로 쪼갰습니다.

```text
개인용 YouTube 학습 사이트를 설계한다.

목표:
- 좋은 영상을 빠르게 찾는다.
- 핵심 구간만 본다.
- 프롬프트와 코드를 복사해 직접 실행한다.

먼저 코드를 작성하지 말고 다음만 제안하라.
1. 핵심 사용자 흐름
2. v0.1에 포함할 기능
3. v0.1에서 제외할 기능
4. 필요한 화면과 데이터
5. 예상 위험
6. 확인이 필요한 결정

확인되지 않은 내용은 추측하지 말고 TODO로 표시하라.
```

이 단계에서 로그인, 데이터베이스, AI 자동 분석, 자동 수집처럼 범위가 커지는 기능을 제외했습니다. 작은 첫 버전을 먼저 완성하는 것이 이후 작업의 기준이 됐습니다.

### 2.2 작업 규칙을 파일로 고정하기

대화 중에만 규칙을 말하면 다음 작업에서 잊히기 쉽습니다. 저장소의 `AGENTS.md`에 다음 원칙을 남겼습니다.

- TypeScript와 App Router 사용
- 콘텐츠는 검수된 JSON/MDX로 관리
- 프롬프트와 코드 샘플은 실행하지 않고 문자열로 처리
- 외부 HTML, JSX, 스크립트를 실행하지 않음
- 테스트와 빌드 결과를 보고
- 확인되지 않은 정보는 TODO로 표시
- 비밀정보와 `.env*` 파일을 커밋하지 않음

AI에게 작업을 시킬 때는 “기존 규칙을 먼저 읽고 따르라”고 명시하면, 매번 같은 안전 기준을 반복해서 설명하지 않아도 됩니다.

### 2.3 콘텐츠와 코드를 분리하기

영상 설명은 사실 검증이 필요한 콘텐츠이고, 화면은 반복해서 바뀔 수 있는 코드입니다. 그래서 다음처럼 분리했습니다.

- `content/*.json`: 영상 메타데이터, 구간, 단계, 요약, 출처
- `content/reviewed/*.mdx`: 검수된 서술 콘텐츠
- `lib/content/schema.ts`: 콘텐츠 구조 검증
- `components/`: 콘텐츠를 화면에 표시하는 컴포넌트

AI에게 콘텐츠를 작성시킬 때는 “영상 원문이나 자막이 없으면 생성하지 말라”고 제한했습니다. 그 결과 출처, 검수 상태, TODO를 데이터 구조에 포함할 수 있었습니다.

## 3. 구현 단계에서 AI를 사용하는 순서

### 3.1 먼저 저장소를 읽게 하기

구현 요청 전에 다음을 확인하게 했습니다.

```text
코드를 수정하기 전에 저장소를 조사하라.

확인할 것:
- 현재 폴더 구조
- package.json과 실행 명령
- 기존 화면과 컴포넌트
- 테스트 파일과 테스트 방식
- 환경변수와 외부 API 사용 여부
- 현재 변경사항

아직 수정하지 말고 현재 구조, 재사용할 코드, 위험 요소만 보고하라.
```

이 과정을 거치면 이미 있는 컴포넌트를 중복 작성하거나, 기존 테스트를 깨뜨리는 일을 줄일 수 있습니다.

### 3.2 한 번에 하나의 작업만 요청하기

실제 구현은 다음과 같이 단계적으로 진행됐습니다.

1. 첫 번째 검수 영상 학습 화면과 콘텐츠 구조
2. YouTube URL 파싱과 제목 조회
3. 개인 영상 목록, 상태, 메모, JSON 백업
4. 반응형 UI와 360px 화면 검증
5. 콘텐츠 JSON Schema와 데이터 기반 학습 워크스페이스
6. 두 번째 영상 추가와 단계 수 일반화
7. `localStorage`에서 IndexedDB로 마이그레이션
8. BroadcastChannel 다중 탭 동기화
9. Vercel 배포와 Web Vitals 연결

각 단계의 요청에는 항상 범위, 수정 대상, 금지사항, 검증 명령을 함께 넣었습니다.

```text
이번 작업에서는 [기능명]만 구현하라.

수정 범위:
- [파일 또는 디렉터리]

하지 말 것:
- 새 인증, DB, 외부 API 추가 금지
- 관련 없는 UI 변경 금지
- 확인되지 않은 콘텐츠 생성 금지

완료 후 실행:
1. lint
2. typecheck
3. 관련 테스트
4. production build

변경 파일, 테스트 결과, 남은 위험을 요약하라.
```

### 3.3 데이터 구조를 먼저 고정하기

화면부터 만들면 나중에 영상이 늘어날 때 하드코딩이 남습니다. 이 프로젝트는 먼저 다음을 정했습니다.

- `schemaVersion`
- 영상의 `youtubeId`, 제목, 채널, 길이
- 필수·선택 구간의 `start`, `end`
- 영상별 `totalSteps`, `stepLabels`
- 백업 JSON의 검증 규칙

AI에게는 다음처럼 경계 조건을 명시했습니다.

```text
콘텐츠 스키마를 추가하라.

검증 조건:
- start < end
- 구간끼리 겹치지 않음
- 영상 길이를 넘지 않음
- required 최대 5개
- optional 최대 3개
- totalSteps는 1~10
- 확인되지 않은 값은 TODO

스키마 테스트와 잘못된 데이터 테스트도 함께 추가하라.
```

이렇게 하면 AI가 예시 데이터를 그럴듯하게 만드는 것보다, 유효한 데이터와 잘못된 데이터를 구분하는 데 집중합니다.

## 4. 테스트와 리뷰에서 AI를 사용하는 방법

### 4.1 구현 직후 테스트하기

테스트는 마지막에 한 번만 실행하지 않았습니다. 기능 단위로 바로 실행해 오류의 원인을 좁혔습니다.

```text
방금 변경한 기능의 동작을 검증하라.

확인할 것:
- 정상 입력
- 빈 값과 잘못된 값
- 중복 데이터
- 저장 실패와 복원 실패
- 새로 고침 후 상태 유지
- 모바일 360px 레이아웃

테스트를 먼저 추가하거나 기존 테스트를 보완한 뒤 실행 결과를 보고하라.
```

최종적으로 로컬 검증은 lint, typecheck, Vitest 142개, webpack build, Playwright E2E 15개까지 수행했습니다.

### 4.2 AI에게 코드 리뷰만 먼저 시키기

수정과 리뷰를 한 요청에 섞지 않고, 먼저 문제 목록만 받았습니다.

```text
현재 변경사항만 리뷰하라. 아직 파일을 수정하지 마라.

우선순위:
1. 데이터 손실과 보안 문제
2. 요구사항 위반
3. 기존 기능 회귀
4. 모바일 레이아웃 문제
5. 테스트 누락

각 문제에 파일 경로와 줄 번호, 재현 조건, 심각도를 포함하라.
문제가 없으면 없다고 명확히 말하라.
```

그 다음 별도 요청으로 높은 심각도와 중간 심각도 문제만 수정하게 했습니다. 이 방식은 AI가 스스로 만든 코드를 무조건 정당화하는 것을 줄여 줍니다.

### 4.3 테스트 결과를 직접 해석하기

AI가 “통과했다”고 말한 것만 믿지 않고 명령의 종료 결과를 확인했습니다.

- `npm run lint`
- `npm run typecheck`
- `npm test`
- `npm run build -- --webpack`
- `npm run test:e2e`
- `git diff --check`

특히 배포 확인은 자동 테스트와 분리했습니다. 로컬 테스트 통과는 Vercel URL 접근, Lighthouse 점수, Analytics 데이터 수집을 의미하지 않습니다.

## 5. 배포 단계에서 AI를 사용하는 방법

### 5.1 배포 전 체크리스트를 요청하기

```text
배포하지 말고 현재 저장소의 배포 준비 상태만 점검하라.

확인할 것:
- package.json의 Node.js engines
- next.config 설정
- build -- --webpack 성공 여부
- 환경변수와 비밀정보 노출 여부
- 정적 라우트와 동적 라우트
- 배포 후 확인할 URL 목록
- Analytics와 Web Vitals 연결

확인하지 못한 항목은 미확인으로 표시하라.
```

이 프로젝트에서는 Node.js `>=20`, webpack 빌드, `/`, `/learn/first-video`, `/learn/second-video` 경로, `@vercel/analytics`, `useReportWebVitals` 연결을 확인했습니다.

### 5.2 배포는 사람이 승인한 뒤 실행하기

AI에게 배포 권한을 무조건 주지 않고, 먼저 변경사항과 환경변수를 검토한 뒤 Vercel에서 GitHub 저장소를 연결했습니다.

- 빌드 명령: `npm run build -- --webpack`
- 운영 URL: `https://vibe-learning-blush.vercel.app/`
- 비밀정보: Vercel 환경변수에만 등록
- 배포 후: 세 라우트 접근과 콘텐츠 단계 수 확인

AI에게 배포 결과를 정리시킬 때도 다음처럼 사실과 미확인을 분리합니다.

```text
배포 결과를 다음 표로 정리하라.

| 항목 | 확인 결과 | 근거 |

URL 응답, 라우트 렌더링, 빌드 로그는 확인된 사실로 작성하라.
Lighthouse, Analytics 대시보드, 실제 두 탭 측정처럼 확인하지 않은 것은 미확인으로 남겨라.
```

## 6. 이 프로젝트에서 얻은 AI 사용 원칙

### 잘 작동한 방식

- 계획과 구현을 분리한다.
- 작업 단위를 한 기능으로 제한한다.
- 기존 파일과 테스트를 먼저 읽게 한다.
- 포함 범위와 금지 범위를 동시에 적는다.
- 데이터 검증 규칙을 자연어가 아니라 조건으로 쓴다.
- 구현 직후 테스트하고, 별도 요청으로 리뷰한다.
- 결과 보고에 변경 파일, 명령, 남은 위험을 포함한다.
- 실제 배포·운영 확인과 로컬 검증을 구분한다.

### 피해야 할 방식

- “알아서 완성해라”처럼 범위가 없는 요청
- 한 번에 UI, DB, 인증, 배포를 모두 요구하기
- AI가 만든 요약과 출처를 검증 없이 사실로 사용하기
- 테스트를 실행하지 않고 성공했다고 기록하기
- 기존 변경사항을 확인하지 않고 파일을 덮어쓰기
- API 키나 운영 토큰을 프롬프트에 붙여 넣기
- 로컬 build 성공을 실제 배포 성공으로 간주하기

## 7. 재사용 가능한 작업 템플릿

```text
현재 저장소의 규칙과 변경사항을 먼저 읽어라.

작업 목표:
- [사용자에게 필요한 결과]

이번 작업 범위:
- [작업 1]
- [작업 2]

완료 조건:
- [검증 가능한 조건]

금지사항:
- 관련 없는 파일 수정 금지
- 새로운 인증/DB/API 추가 금지
- 확인되지 않은 정보 생성 금지
- 비밀정보를 출력하거나 저장하지 않음

진행 순서:
1. 현재 구현과 관련 테스트 조사
2. 구현 계획을 짧게 보고
3. 승인된 범위만 수정
4. 관련 테스트 실행
5. lint, typecheck, build 실행
6. 변경 파일, 실행 명령과 결과, 남은 위험 보고
```
