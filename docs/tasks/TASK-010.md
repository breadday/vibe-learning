# TASK-010: 지연된 자동 제목 응답 E2E 경합 제거

## 목표

`e2e/youtube-title.spec.ts`의 지연 응답 테스트에서 라우트 핸들러가 준비되기 전에 응답 해제 콜백을 호출해 Playwright가 종료되지 않을 수 있는 경합 조건을 제거한다.

테스트가 자동 제목 요청의 시작을 확실히 확인한 뒤 응답을 해제하도록 동기화하고, TASK-007의 사용자 입력 제목 우선 동작을 안정적으로 검증한다. 제품 기능은 변경하지 않는다.

## 배경

다음 E2E 테스트는 자동 제목 API 응답을 의도적으로 지연한다.

```text
keeps a user-entered title when a delayed automatic response arrives
```

현재 테스트 흐름은 다음과 같다.

1. `/api/youtube-title` 라우트 핸들러가 응답 해제 함수를 `releaseResponseRef.current`에 저장한다.
2. 화면에서 `영상 제목을 가져오는 중입니다.` 안내를 기다린다.
3. 사용자가 직접 제목을 입력한다.
4. `releaseResponseRef.current?.()`를 호출해 API 응답을 완료한다.

그러나 `loading` 상태는 `fetch` 호출 직전에 화면에 반영될 수 있다. 따라서 안내 문구가 보이더라도 Playwright 라우트 핸들러가 이미 실행되어 해제 함수를 등록했다고 보장할 수 없다.

이 순서가 발생하면 optional call은 `null`에 대해 아무 작업도 하지 않고, 라우트 핸들러의 Promise는 해제되지 않는다. 테스트 본문의 assertion이 끝나더라도 미완료 라우트 처리가 남아 E2E 프로세스와 CI가 종료되지 않을 수 있다.

- `npm run lint`: 통과

문제 위치는 `e2e/youtube-title.spec.ts`의 지연 응답용 라우트 핸들러와 `releaseResponseRef.current?.()` 호출 사이이다.

## 요구사항

### 1. 라우트 준비와 응답 해제 동기화

- 테스트는 라우트 핸들러가 실제 요청을 받았다는 준비 신호를 명시적으로 제공해야 한다.
- 사용자 제목을 입력하기 전에 자동 제목 요청이 실제로 시작됐음을 확인해야 한다.
- 응답 해제는 준비 신호를 기다린 뒤 실행해야 한다.
- 해제 함수가 없을 때 조용히 넘어가는 optional call을 사용하지 않는다.
- 응답 해제 함수는 정확히 한 번만 실행되어야 한다.
- 테스트 성공·실패와 관계없이 보류 중인 라우트 Promise가 남지 않아야 한다.

권장 방식은 두 개의 명시적 제어점을 사용하는 것이다.

```text
requestStarted: 라우트 핸들러가 요청을 받은 시점에 resolve
releaseResponse: 테스트가 사용자 제목 입력을 마친 뒤 resolve
```

테스트 본문은 `requestStarted`를 기다린 다음 사용자 제목을 입력하고 `releaseResponse`를 호출한다. 실제 구현에서는 resolve 함수의 초기화 여부를 타입과 런타임에서 명확하게 보장해야 한다.

### 2. 사용자 동작 검증 유지

- API 응답 전에 사용자가 입력한 제목이 응답 후에도 유지되어야 한다.
- 자동 제목 응답은 사용자 제목을 덮어쓰지 않아야 한다.
- `영상 제목을 자동으로 입력했습니다.` 성공 안내가 표시되지 않아야 한다.
- 테스트는 API 응답이 실제로 완료된 뒤 위 결과를 검증해야 한다.
- 실제 Google API와 `YOUTUBE_API_KEY`에 의존하지 않는다.

### 3. 회귀 방지

- A → B → A 자동 제목 캐시 테스트를 변경하거나 약화하지 않는다.
- 자동 제목 정상 입력, 사용자 수정, API 실패 후 수동 폴백 테스트를 유지한다.
- 제품 코드 변경 없이 E2E 테스트 동기화만으로 해결하는 것을 우선한다.
- 제품 코드 결함이 별도로 확인되는 경우 임의로 수정하지 말고 결과서에 보고한다.

## 작업 절차

### 1. 사전 확인

다음 파일을 먼저 읽는다.

- `AGENTS.md`
- `docs/tasks/TASK-007.md`

`git status --short`와 관련 diff를 확인하고 기존 사용자 변경을 보존한다.

### 2. 실패 상태 확인

- 지연 응답 테스트만 단독 실행해 현재 대기 현상을 확인한다.
- 실행에는 유한한 제한 시간을 두어 무기한 대기하지 않게 한다.
- 재현되지 않더라도 코드상 가능한 순서와 미완료 Promise 경로를 근거로 수정한다.

### 3. 테스트 동기화 수정

- 라우트가 요청을 받은 시점을 알리는 Promise를 테스트 시작 전에 생성한다.
- 라우트 핸들러는 준비 신호를 보낸 뒤 응답 해제 신호를 기다린다.
- 테스트 본문은 준비 신호를 기다리고 사용자 제목을 입력한 뒤 응답을 해제한다.
- 응답 완료 여부까지 기다린 다음 제목 보존 및 성공 안내 미표시를 검증한다.
- 테스트 실패 시에도 라우트가 영구 대기하지 않도록 정리 경로를 고려한다.

### 4. 반복 안정성 검증

수정한 지연 응답 테스트를 최소 10회 반복 실행한다. 모든 실행이 성공하고 각 프로세스가 정상 종료되는지 확인한다.

반복 실행 명령이나 Playwright 옵션은 저장소에 새 스크립트로 추가하지 말고 작업 중 검증 명령으로만 사용한다.

### 5. 전체 검증

저장소 루트에서 다음 명령을 각각 실행한다.

```text
npm run lint
npm run typecheck
npm test
npm run build -- --webpack
npm run test:e2e
```

각 명령의 종료 코드와 실제 통과 개수를 기록한다. 실행하지 못했거나 종료되지 않은 명령은 성공으로 기록하지 않는다.

E2E 실행으로 `next-env.d.ts`가 `.next-e2e/dev`를 참조하도록 바뀌면 생성된 부수 변경임을 확인하고, 검증 완료 후 기존 `.next/dev` 참조로 복원한다. 복원 전후 diff를 확인한다.

### 6. 결과 문서 갱신

- `docs/tasks/TASK-007-RESULT.md`의 E2E 성공 기록은 이번 전체 E2E가 정상 종료된 경우에만 유지한다.
- 정상 종료되지 않거나 실패하면 해당 결과를 사실대로 정정한다.
- `docs/tasks/TASK-010-RESULT.md`에 원인, 수정 방식, 반복 실행 횟수, 전체 검증 결과와 남은 위험을 기록한다.
